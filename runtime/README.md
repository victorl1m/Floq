# floq-runtime

Cloud runtime that runs Claude Code and Codex CLI sessions inside a container, each behind a PTY, and streams them to Floq over WebSocket. Users sign in with [better-auth](https://better-auth.com) (email + password, bearer tokens); their settings and credentials live in PostgreSQL. Organization collaboration and Tasks use Prisma ORM 7 and the PostgreSQL driver adapter in a dedicated `collaboration` schema. Better Auth and the pre-existing runtime tables keep their existing migration owners and data.

## Deploy on Dokploy

1. Create a **Compose** service, source = this repo, compose path `runtime/docker-compose.yml`.
2. Environment tab: paste `.env.example` and fill every secret (commands are in the comments). Set `BETTER_AUTH_URL` to your public https URL and `FLOQ_BOOTSTRAP_ADMIN_EMAIL` for the first account (no password in env; read the one-time setup token from the logs: see First run).
3. Domains tab: service `runtime`, port `8787`, HTTPS on. Do not add host ports.
4. Deploy. Postgres (`db`) starts first. Runtime startup applies the checked-in Prisma migrations to the isolated `collaboration` schema, then runs the existing idempotent app bootstrap and Better Auth migrations. The database role needs permission to create that schema and its tables.
5. In Floq point the runtime URL at your domain and sign in.
6. Updates: Settings › Runtime › Updates › **Update runtime** rebuilds the runtime from the newest GitHub release and swaps its container in place (same env, volumes, networks); if the new container does not start, the old one comes back. It uses the Docker socket that `docker-compose.yml` mounts at `/run/floq-docker.sock` (hidden from agent sandboxes); remove that volume to disable in-app updates. `FLOQ_UPDATE_RUNTIME_COMMAND` (JSON argv) overrides it with your own deploy script.

## First run (admin account)

There is no password in the environment. Set `FLOQ_BOOTSTRAP_ADMIN_EMAIL`. Knowing that email is not enough to claim the account: while it has no account, the runtime issues a one-time **setup token** at start and prints it once to its logs (look for `FLOQ SETUP TOKEN`). Only a SHA-256 hash is stored (table `setup_token`); if the runtime restarts before the account is claimed, a new token replaces the old one. In the app, choose **Set up the administrator** on the sign-in screen and enter the token, the email, a password (12-128 chars) and optionally a name and company name. The app sends `POST /v1/setup/admin` with `{email, password, setupToken, name?, companyName?}`; the token is marked used as soon as the account exists, then the admin signs in normally.

`POST /v1/setup/lookup` takes `{email, setupToken?}` and answers `{"step":"setup"}` only for the bootstrap email with a valid unused token; for every other input (no token, wrong token, other email, account already exists) it answers `{"step":"password"}`, so it cannot be used to discover accounts or claimable state. `POST /v1/setup/admin` answers 403 `setup_unavailable` with one message for a missing, wrong or used token, an unknown email, and an already-claimed account. Setup creates the Better Auth account plus its initial owner organization atomically; if the company name is blank the organization is named `<first name>'s Organization` (email local part, then `Admin`, as fallbacks). Both routes are unauthenticated and rate limited per IP (10/min).

## Joining an organization

Public signup stays off unless `FLOQ_ALLOW_SIGNUP=1`. A person without an account can use the login screen's **Join with an invitation** flow with the 7-day single-use token, the invited email, a name, and a 12-128 character password. Registration creates a member account only when the invitation is valid and the email matches; creating the account, membership, and consuming the token happen in one database transaction. The runtime does not email invitations: the organization owner shares the raw token with the invited person. Existing accounts sign in with the invited email and accept the token in Floq. A token is never included in a URL.

## Subscription logins and git identity

- Agents use the user's Claude / ChatGPT subscription, not API keys. `POST /v1/providers/:claude|codex/login` opens a login terminal (`claude auth login` / `codex login --device-auth`) in the user's sandbox with a throwaway config dir; the resulting OAuth credential is imported into Postgres (AES-GCM, AAD `<userId>:<provider>_oauth`) and the temp dir is deleted.
- The runtime owns refresh: a background loop refreshes before expiry (Claude when under 30 min are left; Codex when the access token has under 1 h left or `last_refresh` is over 7 days old) against the token endpoints and public client ids the installed CLIs use (`FLOQ_CLAUDE_OAUTH_TOKEN_URL`/`_CLIENT_ID`, `FLOQ_CODEX_OAUTH_TOKEN_URL`/`_CLIENT_ID` override them). One refresh runs at a time per user and provider (in-process plus a Postgres advisory lock) and the rotated refresh token is saved before use. `invalid_grant` marks the login disconnected ("Sign in again"); other failures back off exponentially.
- Before a session starts the credential file is written (0600) to `~/.claude/.credentials.json` or the session's `CODEX_HOME/auth.json`; after each refresh the files of live sessions are rewritten. If a CLI refreshes by itself, its newer credential is adopted into Postgres. `DELETE /v1/providers/:id/login` removes the stored credential and the files.
- Commit author is the user (settings `gitName`/`gitEmail`, else the connected GitHub identity `<id>+<login>@users.noreply.github.com`, else the Floq account). `FLOQ_GIT_COAUTHOR` (default `floqless <floq@flowless.app>`, empty disables it server-wide) is added as a `Co-authored-by` trailer by a system `commit-msg` hook that also strips Claude Code's and Codex's own trailers; users can turn it off with the `gitCoauthor` setting (`gitCoauthorAvailable` is false when the server disabled it). Claude Code's own attribution is disabled in each user's `~/.claude/settings.json` and its PR text becomes "Generated with Floq (https://floq.flowless.app)" while the co-author is on. Repositories with their own `core.hooksPath` (e.g. husky) override the system hook and get no trailer.

## Prompt cache (Claude Code)

Floq sessions sign in with the user's subscription, so Claude Code already uses a 1h prompt-cache TTL there (5m on an API key, Bedrock or Vertex), and every cache read refreshes the timer for free. That is the warming: Floq does not send keepalive turns. These variables only matter when you want to override the CLI. The setting keys behind them (`promptCacheTtl`, `subagentPromptCacheTtl`, `DISABLE_PROMPT_CACHING`) are Claude Code internals as of 2.1.319 and may be renamed; the default `auto` writes nothing, so a rename is harmless.

| Variable | Values | Effect |
| --- | --- | --- |
| `FLOQ_CACHE_TTL` | `auto` (default), `5m`, `1h` | Main-conversation TTL. `5m`/`1h` write `promptCacheTtl` into each user's generated `~/.claude/settings.json` (a value the user set there themselves wins; Floq records what it wrote under `floqManaged` and removes its own value when the setting goes back to `auto` or changes, but never touches a different one). Forcing `1h` changes nothing on a subscription within its limits; on extra usage it doubles the cache write cost (2x instead of 1.25x), so leave `auto` unless you need it. |
| `FLOQ_CACHE_HELPER_TTL` | `auto` (default), `5m`, `1h` | TTL for small helper calls outside the main conversation (`subagentPromptCacheTtl`). The CLI's own subagents are blocked in Floq, so this is rarely worth changing. |
| `FLOQ_CACHE_DISABLE` | `1` to turn off | Debug only: sets `DISABLE_PROMPT_CACHING=1` for Claude sessions (forced after the vault, so a vault secret cannot undo it). Every request becomes a full-price cold write. |

Invalid values fall back to `auto`.

## Host requirements

- `/dev/fuse` and the capabilities in `docker-compose.yml` (see the comment there).
- Ubuntu >= 25.04 hosts confine `/usr/bin/fusermount3` with an AppArmor profile (enforce mode) that only allows FUSE mountpoints under `$HOME`, `/mnt`, `/media`, `/tmp` and `/run/user`. That is why decrypted homes are mounted under `/mnt/floq` (`FLOQ_MOUNT_ROOT`) while the ciphertext stays on the `shards` volume (`FLOQ_SHARD_ROOT`). - Docker's default seccomp profile blocks `pivot_root`, which bubblewrap needs, so the runtime uses `seccomp-floq.json` (Docker's default profile for 29.8.x with `pivot_root` allowed for `CAP_SYS_ADMIN`; regenerate it when upgrading Docker). Never use `seccomp:unconfined`.
- Ubuntu hosts attach the AppArmor profile `bwrap` to `/usr/bin/bwrap` and confine its children as `unpriv_bwrap` (no `CAP_SETUID`), so the image runs an identical copy, `/usr/local/bin/floq-bwrap`.
- A mountpoint on the volume fails with `fusermount3: mount failed: Permission denied` and `apparmor="DENIED" ... profile="fusermount3"` in `dmesg`.

## Security model

- Auth: better-auth, passwords hashed with scrypt, min length 12, DB-backed rate limits (5 sign-ins/min), 7-day sessions, secure cookies on https, trusted origins from `FLOQ_ALLOWED_ORIGINS` (wildcards rejected). Signup is off unless `FLOQ_ALLOW_SIGNUP=1`.
- Isolation: every session, workspace (`/workspaces/<userId>`) and API route is scoped to the authenticated user; other users' sessions return 404.
- Credentials: Anthropic/OpenAI keys and GitHub tokens are encrypted with AES-256-GCM (`FLOQ_ENCRYPTION_KEY`, bound to user and field) and only decrypted when a session starts. Settings responses never return secrets. Server-wide provider keys are not inherited by sessions.
- Agents run as an unprivileged user in the container. Auto-approve (Claude `--dangerously-skip-permissions`, Codex `--dangerously-bypass-approvals-and-sandbox`) defaults to on per provider and each user can turn it off in Settings. With it on, an agent can run arbitrary commands in the container.
- Shards: every user gets a numeric uid and a gocryptfs-encrypted home (`/var/lib/floq/shards`). The per-user data key is random, stored in Postgres wrapped with `FLOQ_ENCRYPTION_KEY`, and only used to mount the home while the user has a terminal open. Agents run in a bubblewrap sandbox (own PID/IPC/UTS namespaces, only that user's home mounted, read-only system dirs, no capabilities, `no-new-privs`). Nothing is mounted or running for a user who has no terminal open.
- Network isolation is on by default (`FLOQ_NETNS=required`, below): every user's sandboxes run in their own network namespace, so an agent cannot reach other users' loopback ports or abstract sockets, the `db` host, or the runtime port except the API gateway; outbound internet still works through pasta. The runtime refuses to start if the host cannot provide this. `FLOQ_NETNS=off` restores the old shared network (single-tenant or fully trusted hosts only: agents can then reach the runtime port, the `db` host and other users' loopback). If you opt out, keep `POSTGRES_PASSWORD` strong and add egress rules on the VM.
- Put it behind TLS (Dokploy/Traefik does this) and keep Postgres unpublished.

## HTTPS dev servers (mkcert)

`next dev --experimental-https` and similar tools work in agent sandboxes. The image ships `mkcert` (1.4.4, sha256-pinned in the Dockerfile) and `certutil` (`libnss3-tools`). Agent sessions get `CAROOT=$HOME/.local/share/mkcert` and `TRUST_STORES=nss`, so `mkcert -install` needs no root: it creates the CA in the user's encrypted home and adds it to `$HOME/.pki/nssdb`, an empty NSS database seeded into every home from the skeleton (`image/build-skel.sh`). The shared agent Chromium (`floq-browserd`) runs as the same user with the same `HOME` and reads that database, so `https://localhost:PORT` of a dev server in that sandbox loads without a certificate warning (reload the page; restart the browser if a warning persists after installing the CA while it was running). The CA is per user and only trusted by that user's own browser; nothing is installed system-wide (see [SECURITY.md](../SECURITY.md)).

## Chromium's own sandbox (`FLOQ_BROWSER_SANDBOX`)

The agent browser runs Chromium inside the user's bubblewrap sandbox. Chromium adds its own namespace sandbox on top (user, PID and network namespaces plus seccomp-bpf), which needs `unshare(CLONE_NEWUSER)` and a write to `/proc/self/uid_map`.

**Why it failed in production.** The container ran with `apparmor:unconfined`. On Ubuntu 23.10+/24.04 hosts `kernel.apparmor_restrict_unprivileged_userns=1` lets an unconfined process create a user namespace but gives it no capabilities there, so `unshare -U` works while the uid_map write fails with `EPERM` and Chromium aborts with "No usable sandbox". The seccomp filter, `max_user_namespaces`, `NoNewPrivs` and the empty capability set are not the cause. The setuid `chrome-sandbox` is not an option (`no-new-privs`).

**Fix (host, once).** Load the shipped profile, which only adds `userns,` to the old unconfined behaviour, and start the stack with it:

```
sudo cp runtime/apparmor/floq-runtime /etc/apparmor.d/floq-runtime
sudo apparmor_parser -r /etc/apparmor.d/floq-runtime
FLOQ_APPARMOR_PROFILE=floq-runtime docker compose up -d     # default is still `unconfined`
```

Check from an agent terminal: `cat /proc/self/attr/current` prints `floq-runtime (unconfined)` and `unshare -Ur true` succeeds; then `floq browser status` shows `sandbox: chromium sandbox on`.

| Variable | Default | Meaning |
|---|---|---|
| `FLOQ_BROWSER_SANDBOX` | `auto` | `required`: Chromium must start with its sandbox, otherwise the browser fails to start with a clear error (no `--no-sandbox`). `auto`: try the sandbox, fall back to `--no-sandbox` and log `browser.chromium_sandbox_off` at warn level with the reason. Set `required` once the profile is loaded. |
| `FLOQ_APPARMOR_PROFILE` | `unconfined` | AppArmor profile name for the runtime container in `docker-compose.yml`. |

## Per-user network namespaces (`FLOQ_NETNS`, on by default)

`FLOQ_NETNS` unset or `required` (the default) gives every user one persistent network namespace (`/run/floq/netns/<uid>`, created with `unshare --net=<file>`); all of that user's sessions share it, other users cannot see its loopback ports or abstract sockets (X11 `@/tmp/.X11-unix/Xn`). The runtime refuses to start when namespaces are unavailable (fail fast: the error names the missing piece, the host requirements and the opt-out). `FLOQ_NETNS=1` isolates when possible but logs `netns.disabled` and falls back to the shared network on a failed probe. `FLOQ_NETNS=off` (or `0`) disables isolation: single-tenant or fully trusted hosts only.

**Host requirements:** Linux kernel with network namespaces and nftables; the container needs `CAP_SYS_ADMIN` and `CAP_NET_ADMIN` (both in `docker-compose.yml`; a custom compose must add `NET_ADMIN`); a seccomp profile that allows `unshare`/`setns` for those caps (the bundled `seccomp-floq.json` does); the image tools `unshare nsenter setpriv socat nft ip floq-pasta`. The Dokploy/compose deployment gets all of this from the repo. Local development on a Linux host without these should set `FLOQ_SHARD_DRIVER=local` or `FLOQ_NETNS=off`.

**Verified vs host-verified:** the argv/ruleset builders, mode parsing and the fail-fast path are unit-tested. Cross-tenant blocking, pasta outbound internet, runtime→db (the runtime itself is not namespaced, so its Postgres connection is unaffected), the browser daemon (it runs inside the user's sandbox and so inside the namespace; the runtime reaches it with the same `nsenter`+`socat` tunnel as dev ports, and user-IP egress dials out from the desktop over the runtime WebSocket, not from the sandbox) and port forwarding need a real multi-tenant host: run `sudo scripts/netns-smoke.sh` there after deploy.

- Launch: `nsenter --net=<path> -- floq-bwrap ...` (bwrap inherits the namespace; setpriv still drops to the user's uid).
- Connectivity: one `floq-pasta` (pinned upstream passt build, a copy of `pasta` like `floq-bwrap`; Debian bookworm's passt predates `--map-host-loopback`) per user, started with `--runas 0` so it can keep its pid file, attached by path, with no inbound forwards. `10.255.255.1` is the gateway and maps to the runtime's `127.0.0.1`, so `FLOQ_API_URL` becomes `http://10.255.255.1:<FLOQ_PORT>` (the runtime must listen on loopback/all interfaces). DNS goes through pasta's forwarder (`10.255.254.53`), the sandbox gets its own `resolv.conf`.
- Egress policy (nftables, inside the namespace): default drop; allows DNS, `gateway:<FLOQ_PORT>` and public IPv4; drops RFC1918, CGNAT, link-local/cloud metadata, reserved ranges and every other gateway port (so the `db` is unreachable). `FLOQ_NETNS_ALLOW=cidr,cidr` accepts extra IPv4 destinations before the drops (e.g. an internal git host). IPv6 is off.
- Host public address (hairpin): the host's own public egress address is dropped too. Through pasta a tenant could otherwise connect to that address and reach every service the host publishes on it (other projects' databases, a Dokploy panel, SSH). Discovery, at runtime start and then every `FLOQ_HOST_PUBLIC_IP_REFRESH_SECS` (default 300): `FLOQ_HOST_PUBLIC_IPS=ip,ip` (comma-separated IPv4/IPv6, validated; set this on multi-tenant hosts, it does not depend on any outside service) plus auto-detection of the egress address through `FLOQ_HOST_PUBLIC_IP_URL` (default `https://api.ipify.org`, must return a bare IP, 4 s timeout; `off` disables). When the detected address changes the rules of every live namespace are replaced atomically and the old address stops being dropped; a failed detection keeps the last known address and is retried (every 30 s until the first success) with a `netns.public_ip_detect_failed` warning; with nothing configured or detected the runtime logs `netns.public_ip_unknown`. Detection only adds protection, so it never prevents a start. IPv6 entries are accepted but need no rule (namespaces drop all IPv6). `gateway:<FLOQ_PORT>` stays the only reachable host-side port. Internet egress to every other public address is unchanged.
- Ports and tunnels: detection reads `/proc/<session pid>/net/tcp`; the port tunnel connects with `nsenter --net=<path> -- socat` (needs `socat` in the image); the display port probe checks inside the namespace.
- Lifecycle: created when the user's shard wakes, removed when it sleeps; leftovers are cleaned at runtime start. Needs `CAP_SYS_ADMIN` (already required for bwrap/FUSE) and the image packages `passt socat nftables iproute2`.
- Verify on a real host: `cd runtime && npm run build && sudo SMOKE_HOST_PUBLIC_IP=$(curl -4s https://api.ipify.org) scripts/netns-smoke.sh` (`SMOKE_HOST_PUBLIC_IP` enables the hairpin checks against ports 22, the db port and the runtime port on the public address; without it they are skipped with a warning).

## Agent memory (optional)

Agents and the user can keep durable facts, decisions, procedures and episodes (`floq memory add|search|list|read|update|forget`, and the Memory dialog in the app). It is off unless `FLOQ_REDIS_URL` is set.

**Nothing to set up.** `docker compose up -d` starts it with the rest. The runtime creates a random API key once in the `wahakey` volume (mounted only by the runtime and, read only, by `waha`); WAHA waits for that file and starts with it. To use your own key set `FLOQ_WHATSAPP_API_KEY` (the runtime writes it to the same file). To turn the built-in server off set `FLOQ_WHATSAPP_BUILTIN=0` and stop the service (`docker compose stop waha`, or remove it from your compose file).

**What Floq configures by itself.** The runtime and WAHA use the same key, so nothing is typed into the app: while the integration's WAHA address is empty it uses `http://waha:3000` with that key, registers its webhook on the compose network (`FLOQ_INTERNAL_URL`, default `http://runtime:8787`, so no public URL is needed) and shows the server's state in Settings (admin only: running, version, health check). You open WhatsApp in Floq and scan the QR code. The server has no host port, its dashboard and Swagger UI are off, the engine is NOWEB (no browser), linked accounts reconnect after a restart, and logs are JSON at `info`. The key never reaches the app or agents; a key under 24 characters is refused (`FLOQ_WHATSAPP_BUILTIN=0` keeps a key but leaves the built-in server unused).

**Data and backup.** `wahasessions` holds the linked accounts (losing it means scanning the QR code again) and `wahamedia` the files WAHA downloads. Media stays local: the built-in server uses no object storage, WAHA deletes its copies after a few minutes, and Floq keeps what it shows in its own database. Back up `wahasessions` with the database. Redeploys and updates keep both volumes.

**Updates.** Settings > Updates lists **WhatsApp server** with the installed version (`GET /api/server/version`) and the newest stable WAHA release (GitHub releases of `devlikeapro/waha`; drafts and pre-releases are ignored). Updating pulls the new image and replaces only the `waha` container through the Docker socket (the mount "Update runtime" uses): same environment, volumes and network, old container parked until the new one passes its healthcheck (3 minutes), otherwise the previous version is started again. Administrators get a notification with the result. Automatic updates are on by default (switch and quiet window in Settings > Updates): the runtime looks once a day and updates when no message was sent or received for 30 minutes (5 to 1440) and no QR login is open; a release that was rolled back is not retried by itself. The tag in `docker-compose.yml` (`FLOQ_WHATSAPP_IMAGE_TAG`, default `noweb-2026.10.1`; ARM hosts use `noweb-arm-2026.10.1`) is the floor: the runtime remembers the release it moved to and puts it back after a redeploy recreated the container on the pinned tag, so a redeploy never downgrades. Only the official image with a versioned tag is managed; without the socket mount, or with another image, the row shows the versions and you update with `docker compose pull waha && docker compose up -d waha`.

**An external WAHA instead.** Enter its address and API key in the integration's settings: a saved address always wins and the built-in key is never sent to it. Webhooks then go to the runtime's public URL (`FLOQ_PUBLIC_URL`, else `BETTER_AUTH_URL`). Floq shows "update available" for an external server but cannot update it.

**Limits of WAHA Core.** One WhatsApp account (one session, named `default`) per server; several accounts need WAHA Plus, which is not open source and not bundled (use it as an external server). Run one WAHA per Floq runtime.

**License and terms.** WAHA Core is licensed under Apache-2.0 by its authors; Floq distributes nothing of it, compose pulls the official image (see [`NOTICE`](../NOTICE)). WAHA is not affiliated with Floq or with WhatsApp. It links WhatsApp as an unofficial client, which WhatsApp's terms do not cover: numbers that send spam or bulk messages can be restricted or banned. Use it for normal conversations.

Env: `FLOQ_WHATSAPP_API_KEY`, `FLOQ_WHATSAPP_BUILTIN`, `FLOQ_WHATSAPP_URL`, `FLOQ_INTERNAL_URL`, `FLOQ_WHATSAPP_IMAGE_TAG`, `FLOQ_WHATSAPP_MEM_LIMIT` (1g), `FLOQ_WHATSAPP_CPUS` (1.0), `FLOQ_WHATSAPP_LOG_LEVEL`. API (admin): `GET /v1/admin/whatsapp-server`, `GET /v1/admin/whatsapp-server/health`, `POST /v1/admin/whatsapp-server/test {baseUrl, apiKey}`, `PUT /v1/admin/whatsapp-server/auto-update {enabled, quietMinutes}`.

## Sleep and resume

A terminal **sleeps** when it has had no input or output for `FLOQ_SESSION_IDLE_TIMEOUT_MS`, hits `FLOQ_SESSION_MAX_LIFETIME_MS`, the user logs out, or the server restarts. Sleeping saves the session (provider, directory, size, last output seq, reason) to Postgres and stops the PTY; the agent's own conversation files stay in the user's encrypted home. When the user has no live terminals, their home is unmounted after `FLOQ_SHARD_LOCK_DELAY_MS`. `POST /v1/sessions/:id/resume` wakes the shard and continues exactly that session's conversation, so several terminals in one project never get mixed up. Claude is started with `--session-id <session uuid>` and resumed with `--resume <uuid>`. Codex picks its own uuid, so each Codex session runs with a private `CODEX_HOME` (`~/.floq/codex/<session id>`); the runtime reads the uuid from the rollout file name, stores it in `agent_sessions.provider_session_id`, and resumes with `codex resume <uuid>`. Auto-approve flags are re-applied. If the conversation id is unknown (nothing was ever sent) or the resume fails immediately, a fresh agent starts instead.

## Vault and agent orchestration

- **Vault** (`GET /v1/vault`, `PUT|PATCH|DELETE /v1/vault/:NAME`; PATCH takes optional `name` (rename, re-encrypts under the new name), `description`, `expose`, `value`; omitted `value` keeps the current one; a taken name returns 409): secrets are encrypted per user (AES-256-GCM, bound to user and name), write-only over the API, audited (names only, never values). `expose: "tool"` (default) secrets are only reachable through `floq-vault run -- cmd` inside a terminal, which injects them into that one command's environment and redacts them from its output. `expose: "env"` secrets are injected into every terminal's environment, which means the agent can read them, so use it only for low-risk values. Access from a terminal uses a per-session token that is revoked when the session sleeps or ends.
`floq session restart` reloads configuration for the calling Claude or Codex agent only. It returns before stopping that PTY, then stops it and resumes the same Floq session UUID, working directory, and provider conversation. A Codex session is not stopped until its provider conversation ID is captured; restart resume disables the ordinary fast-failure fallback that could start a blank conversation. If the old PTY does not stop, its process remains tracked and further resume attempts are blocked until exit. If resume fails, the session is marked failed and the error is logged. Restarting applies config; it does not authenticate an MCP server or prove its tools loaded. Verify the provider's tools after resume. The CLI endpoint derives its target from the authenticated per-session agent token and rejects target IDs and non-POST requests.
Codex startup guidance: at each session start or resume, Floq refreshes a marked block in the effective global `CODEX_HOME/AGENTS.override.md` (when non-empty) or `AGENTS.md`, preserving all surrounding user instructions. It also refreshes Floq's protected `floq-orchestrate` skill copy without removing other skill files. This tells agents to use Floq CLI for coordination and installed-state diagnostics; an MCP being configured does not mean it is authenticated or loaded.
- **`floq` CLI** (preinstalled with the `floq-orchestrate` skill): `floq list | models | ask | check | note ... | recruit | connect | dismiss | skills ... | mcp ... | secrets ...`. Agents (claude/codex, never shells) are linked per project: two sessions can reach each other iff they share the same cwd (sessions on an auto-assigned `workspace/<id>` directory form one scratch project). Only sessions created with `lead: true` (a user choice) may recruit or dismiss, and only inside their own project; recruited agents start in the lead's cwd, and `floq connect` is a no-op within a project and 403 across projects. `ask` types the message into the target's terminal and returns its output once it has been quiet for 5 s (best effort for TUIs), waking a sleeping target first. Notes are shared per user.
- `floq recruit` and `floq subagent recruit` accept `--skill NAME[,NAME]` (max 8): the runtime adds a `[FLOQ RECRUIT SKILLS]` system block on every start and resume telling the recruit to load those skills first (stored in `agent_sessions.recruit_skills`). Use it when the task depends on a skill, e.g. `artifact-design` for an Artifact.
- Preinstalled for agents: `python3` + `pymysql` + `psycopg2`, the `mysql` and `psql` clients.
- The orchestration skill source is `../skills/floq-orchestrate/SKILL.md`; before building the runtime image, run `powershell -NoProfile -ExecutionPolicy Bypass -File ../scripts/sync-floq-orchestrate-skill.ps1` from this directory to synchronize the image copy.

## MCP servers, skills and secrets from the app and the `floq` CLI

- **Install and remove an MCP server** (`POST /v1/mcp` with `{scope, projectId?, providers: "claude"|"codex"|"both", server: {name, type: "stdio"|"http", command, args, url, env, headers}}`; `DELETE /v1/mcp?scope&projectId&provider&name`). Each edit is a read, merge and atomic write of one entry, run inside the user's unprivileged sandbox like the skill installs, so nothing else in the file changes. The files are the ones the CLIs read: Claude Code `~/.claude.json` (global) or the project's `.mcp.json`, and Codex `~/.codex/config.toml` (global) or the project's `.codex/config.toml`. Codex edits append or cut TOML text, so comments and other settings are kept, and the result is parsed and compared before it is written. A malformed existing file is refused and left alone, a duplicate name is a 409, symlinks are refused, and the helper can only touch those four paths. Bundled servers (context7) cannot be removed or replaced. **Secrets in an MCP config.** A value can be a vault reference, written `${vault:NAME}` (a header may embed it: `Bearer ${vault:NAME}`). The app's Add MCP server dialog lets the user pick an existing vault secret or type a new value, which is saved with `POST /v1/vault` semantics (create-only, `tool` exposure; a taken name is a 409 and is never overwritten). Install order: validate, create the new secrets, write the config; if the config write fails, only the secrets created by that attempt are deleted. The config never holds the value. A stdio server is written wrapped as `floq-vault run --stdio --only NAMES --map ENV=NAME -- <command> <args>` (Codex also gets `env_vars = ["FLOQ_API_URL", "FLOQ_AGENT_TOKEN"]`, because it scrubs the MCP child's environment), and `floq-vault` fetches exactly those secrets with the session token when the server starts, passing stdin and stdout through untouched (no buffering or redaction on the JSON-RPC stream; stderr is redacted; a missing secret exits 1 with a clear message). HTTP headers for Claude Code use a `headersHelper` (`floq-vault headers`). Codex cannot do this for HTTP (its `http_headers_helper` runs without the session environment), so a vault reference in a Codex HTTP server is refused rather than written in plain text. A literal value is only stored in the config when the user explicitly keeps it as plain text (the API refuses credential-looking names such as TOKEN, KEY, SECRET, PASS or AUTH unless `allowPlaintext: true`). Env and header values never come back from any route, log or error. This keeps values out of config files and git; it does not hide them from a determined agent, because any agent in the session can run `floq-vault run -- cmd` with a tool-exposed secret. Deleting or renaming a secret breaks the servers that reference it: the server fails to start and `floq-vault` says which secret was not found. Removing a server leaves its secrets in the vault. A project's config can be committed to git, which is safe for references only. Codex sessions run with a private `CODEX_HOME`, so at each start or resume the runtime copies the user's global `mcp_servers` from `~/.codex/config.toml` into that session's config (only servers it does not define; no other settings). New servers load when a session starts or resumes; running sessions keep the old list.
`floq session restart` reloads configuration for the calling Claude or Codex agent only. It returns before stopping that PTY, then stops it and resumes the same Floq session UUID, working directory, and provider conversation. A Codex session is not stopped until its provider conversation ID is captured; restart resume disables the ordinary fast-failure fallback that could start a blank conversation. If the old PTY does not stop, its process remains tracked and further resume attempts are blocked until exit. If resume fails, the session is marked failed and the error is logged. Restarting applies config; it does not authenticate an MCP server or prove its tools loaded. Verify the provider's tools after resume. The CLI endpoint derives its target from the authenticated per-session agent token and rejects target IDs and non-POST requests.
Codex startup guidance: at each session start or resume, Floq refreshes a marked block in the effective global `CODEX_HOME/AGENTS.override.md` (when non-empty) or `AGENTS.md`, preserving all surrounding user instructions. It also refreshes Floq's protected `floq-orchestrate` skill copy without removing other skill files. This tells agents to use Floq CLI for coordination and installed-state diagnostics; an MCP being configured does not mean it is authenticated or loaded.
- **`floq` CLI** (same services, same checks): `floq skills list|search|preview|add|create|remove`, `floq mcp list|add|remove`, `floq secrets list`. Reading is open to any agent session of the user. Adding or removing skills and MCP servers needs a **lead** session (the `recruit` check); plain shell sessions are refused like for `floq list`. `floq mcp add --dry-run` prints exactly what would run (command and arguments or the URL, env and header names with values hidden) and changes nothing.
- Create a project from an agent terminal with `floq project create --name NAME`; pass `--git-url URL` to clone a repository instead. A Git URL can be used without a name to derive the project name. Plain projects get an empty managed workspace; both forms appear in the app's project list.
- **Limit worth knowing:** the CLI cannot make an agent ask the user first. The skills tell agents to get the user's go-ahead before `add`/`remove`, but a prompt-injected lead agent could still run them. A lead agent can already edit its own config files in its home, so MCP and skill install add convenience rather than new reach.

## Claude Code plugins with function hooks

Every Claude session starts with `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1` (set in `forcedSessionEnv`, after vault env, like `CLAUDE_CODE_NO_FLICKER`). Without it, Claude Code reads a plugin's `hooks/hooks.json` but never loads the `modules` it lists, so plugins such as `fast-jev-compaction` silently do nothing. Users could not set it themselves: the env allowlist drops it and `CLAUDE*` is a reserved secret name. Each team member installs plugins in their own home (`claude plugin marketplace add OWNER/REPO`, then `claude plugin install NAME@MARKETPLACE`), and keys a plugin reads from the environment (for example `TYPESAFE_API_KEY`) go in the vault with `expose: "env"`. Running sessions pick the flag up when they restart or resume.

**Plugins that need protected hooks (`session.compact`, prompt content) just work.** Floq ships Claude Code managed settings, and on a machine with managed settings (and for Team and Enterprise organizations) Claude Code seats its built-in `cc-plugin-sec-default` module first, which passes protected events on past every plugin a person installed ("fast-jev-compaction: its session.compact hook was skipped"). So at every Claude session start the runtime gives the user's sandbox its own managed settings, a root-owned folder (`<shardRoot>/meta/<uid>.claude-code`) bound read-only at `/etc/claude-code`: the image's base policy (native-subagent deny) plus every plugin the user enabled, as managed plugins listed in `prependPlugins` ahead of `sec-default@builtin`, which keeps its seat right after them. Claude Code only seats a managed plugin read in place from a local folder, so the runtime keeps a snapshot of each such marketplace in that folder (`/etc/claude-code/plugins/<marketplace>` in the sandbox; cloned as the runtime from the GitHub or https git source the user added it from, git hooks off, refreshed at most hourly, kept when offline) and points the user's own registration of the marketplace at it. Nothing to configure: install and enable plugins the normal way (`/plugin`, `claude plugin install`); they apply from the next session start and show as "Scope: managed". Inside a session Claude Code refuses to disable a managed plugin; to turn one off, set it to `false` under `enabledPlugins` in `~/.claude/settings.json` (or ask an agent to), and the next session drops it. Plugins whose marketplace lists them by a remote source, or that come from a `marketplace.json` URL, stay normal user plugins. Trade-off: every plugin a user or their agent enables runs ahead of Floq's own managed hooks, as on an unmanaged machine. Verified with Claude Code 2.1.318 (normal install, then `/compact`: the plugin loads "tier prepend" and its session.compact hook runs).

## Preinstalled skills

Skill authoring: obra/superpowers already provides `writing-skills` for both providers. The image also bundles Anthropic's `skill-creator` (anthropics/skills, Apache-2.0, LICENSE.txt kept in the skill folder) for Claude Code only, pinned by full commit hash through `ANTHROPIC_SKILLS_REF` (a Docker build arg and a build-skel.sh variable; the build fails if the commit cannot be fetched or does not match). Codex ships its own `skill-creator`, so none is copied for Codex. It is a third-party skill like the others: it follows `PREINSTALL_SKILLS`, can be deleted per user, and is copied into existing homes on the next shard wake (never over existing files). Its scripts need Python 3 with PyYAML (`python3-yaml` is in the image) and its eval and description-optimisation scripts call `claude -p` (they use the user's Claude login); its report viewer pages load fonts and a spreadsheet library from public CDNs when opened in a browser. Its SKILL.md is about 33 KB, so the listing limit for SKILL.md files is 64 KiB while authoring and imports keep 32 KiB.

`floq skills create NAME --description TEXT (--from DIR | --instructions FILE | -) [--provider] [--project [UUID] | --global] [--dry-run]` authors a skill through the same validation and sandboxed write as the app (lead sessions only; a dry run is open to any agent). Project scope is the default when the session has a project, otherwise the user's home (`~/.claude/skills` or `~/.agents/skills`). Duplicates are a 409, Floq's own skill names are refused, and creating a global skill clears that skill's removal record. The request body for this one route may be up to 1.5 MiB (other routes keep `FLOQ_MAX_BODY_BYTES`).

The image bakes third-party skills into a read-only skeleton. `PREINSTALL_SKILLS` (default `0`) controls whether they are copied into user homes (never overwriting existing files) and listed on the Skills page. With it off, only Floq's own `floq-orchestrate` and `floq-vault` skills are seeded and listed, because agents rely on their instructions; the rest of the skeleton (settings, hooks, MCP config) is unaffected. Turning it off does not remove skills that are already in a home. Users can delete any skill except the two Floq skills from the Skills page; the deletion is stored per user in `skill_removals`, honoured when seeding and listing, and touches neither the shared image bundle nor other users. To bring a deleted skill back, delete its `skill_removals` row (user, provider, directory name); it is re-seeded on the next shard wake or Codex session start.

## Selectable models

When `FLOQ_CODEX_MODELS` is unset or empty, authenticated `GET /v1/info` discovers each user's visible Codex models through that user's Codex app-server, including paginated results. Results are cached per user for five minutes; if discovery is unavailable, the runtime uses its built-in fallback, which includes the current catalog (`gpt-6.1-sol`, `gpt-6-astra`, `gpt-6.1-terra`, `gpt-6-sol`, `gpt-6-luna`, `gpt-5.6-sol`, `gpt-5.6-terra`, and `gpt-5.6-luna`) plus previously configured legacy entries. Hidden catalog entries are excluded. A non-empty `FLOQ_CODEX_MODELS` intentionally replaces dynamic discovery, using comma-separated `id:label` entries. Rebuild/restart the runtime after changing code or environment; the app refreshes `/v1/info` every five minutes while connected.

## API

Auth endpoints live under `/api/auth/*` (better-auth). `POST /api/auth/sign-in/email` returns a `set-auth-token` header; send it as `Authorization: Bearer <token>` on everything else (WebSocket: `?token=`).

### Prisma and database ownership

- `runtime/prisma/schema.prisma` and `runtime/prisma/migrations/` own only the `collaboration` schema; task/organization models intentionally keep user IDs as strings and do not add foreign keys into Better Auth's `public.user` table.
- `npm run build` generates the Prisma Client before TypeScript compilation. `npm start` runs `prisma migrate deploy` before starting the runtime; the Docker image includes the Prisma config and migration files.
- For an existing deployment, redeploy the runtime image. The migration is additive and isolated: it creates `collaboration` and its organization/task tables without altering existing public tables or rows. It does not require baselining or marking the legacy schema as Prisma-managed.
- To apply the migration manually in a development environment, set `DATABASE_URL` and run `npm run prisma:deploy` from `runtime`. Do not use `prisma migrate reset` against an existing Floq database.
- Prisma Client uses its own PostgreSQL driver pool in addition to the existing `pg` pool used by Better Auth and legacy services. Keep the database connection limit sized for both.

## Administration and updates

- Instance roles (`admin`/`member`) live in `collaboration.user_roles`. When no administrator exists, the `FLOQ_BOOTSTRAP_ADMIN_EMAIL` user (else the earliest registered user) is promoted once; afterwards administrators manage roles from Settings > Users. The last administrator cannot be demoted.
- `GET /v1/admin/updates`, `POST /v1/admin/updates/apply {target, force}` (admin only). Env: `FLOQ_UPDATE_REPO` (GitHub `owner/name` releases, default `victorl1m/Floq`), `FLOQ_UPDATE_RUNTIME_COMMAND` (JSON argv of an operator deploy script), `FLOQ_UPDATE_RUNTIME_DIR` (git checkout for `git pull` + build). Claude Code and Codex are upgraded with `npm install -g <pkg>@latest`. A runtime update ends with SIGTERM; the container restart policy starts the new build. It replaces only the runtime container: the database, the memory store and the WhatsApp server keep running with their volumes. Target `whatsapp` updates the built-in WhatsApp server (see above; 409 `whatsapp_busy` inside the quiet window unless `force`, `whatsapp_login_active` during a QR login).

### FLOQ_NETNS hardening notes

- Startup probe is real: it creates a throwaway namespace, applies the nft rules, starts pasta and waits for the address, then tears it down. `FLOQ_NETNS=1` disables the feature with a loud log on failure; `required` refuses to start.
- The container's own non-loopback IPv4 addresses are dropped inside every namespace (pasta would otherwise reach host services such as the DB through the public address), plus the documentation ranges and the host's public egress addresses (`FLOQ_HOST_PUBLIC_IPS` and auto-detected; see the egress policy above). Only `gateway:FLOQ_PORT` and DNS are allowed to the host side.
- A pasta that keeps crashing is respawned up to 5 times in a row (the budget resets after 60s of uptime); after that sandbox launches fail with a clear error until the user's workspace is woken again. Tunnels are refused when no live session process exists to read the namespace from, and capped at `FLOQ_NETNS_TUNNEL_LIMIT` (default 32) helper processes per user, run as the user's uid.
